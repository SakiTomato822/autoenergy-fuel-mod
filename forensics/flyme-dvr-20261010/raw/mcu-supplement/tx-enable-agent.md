# MCU TX index 33 使能条件静态分析

范围：只检查 B12 所述的同一份 `3C5525_MB_UPDATE.bin`、其 `data-copy-map.json` 和已有反汇编材料。二进制身份与地址映射沿用 B12；本报告没有运行固件、读写车辆、发帧或联网。

## 结论

`DVRConfig=0` 不是这段 MCU 发送代码可见的直接禁用条件。MCU 收到并接受 UART 模型条目后，会按映射更新 index 33 的待处理状态；周期任务再经过 MCU 自身的任务开关、发送管理器状态、CAN 控制器和邮箱状态判断。ROM 中没有发现该路径读取或比较名为 `DVRConfig` 的字段。`DVRConfig=0` 是否让 AP 根本不发 13/01 UART 更新，属于 AP 侧尚未建立的数据流，不能由这份 MCU 固件单独回答。

`20409804+0x218` 是缓存/事件处理描述表指针槽：槽地址 `20409a1c` 中初始化为 `20409a20`，记录宽 28 字节。该表的第 33 项位于 `20409dbc`，按初始化映射来自固件 VA `49c244`（文件偏移 `7c244`），原始字节为 `01 00 00 00 a4 8f 48 00 08 00 50 00 c1 00 00 00 bd e1 43 00 ...`。此表不是 `435d7e` 的 TX 描述来源：`435d7e` 的反汇编字面量在 `435df8`、`435dfc`、`435e0c` 分别指向 `0x4890bc` 索引映射、`0x2040ae6c` TX 缓冲表和 `0x48b77c` post-send 回调表。`435f28` 才读取 `+0x218` 指针，并由 `436016` 从 RX/cache 候选路径调用；物理 RX 描述表 `20408bbc` 又是另一张表。因此不同表中相同的数值 index 33 不代表同一条消息。

更正：先前版本把 `20409804+0x218` 误称为 TX 描述表，并把其中 index 33 的 `+0x0a=0x50`、`+0x0c=0xC1` 套到 D8 TX 项；这是表身份混淆，现撤回。以下 `0x50/C1` 只讨论缓存/事件处理路径，不作为 D8 TX 的参数、许可或时长证据。发送管理器对象 `204172d4` 仍是独立对象：其 `+0x0c` 为运行期状态字、`+0x04` 为门控位、`+0x08` 为非零就绪字段。

缓存/事件描述项 `+0x0c=0xC1` 不是“禁用”布尔值。TX 提交入口 `435d7e` 和管理器入口 `434744` 不读取 `+0x218` 表。数据准备例程 `435f28` 使用缓存/事件描述项 `+0`、`+4`（该表第 33 项分别为 `1` 和 `0x488fa4`）处理数据/掩码；`+0x0c` 则由 `4366de` 一带的事件处理分支读取，代码用 bit 6、bit 7 选择分支，并在一个路径中作有符号字节判断。其含义限于该缓存/事件路径，不能据此判断 D8 TX 的许可状态。

## 请求进入调度器

B12 已确认 1A8 元数据回调写 `204004d7` 的 byte 1 bit 3；模型解包器 `439984` 根据模型映射记录更新对应的运行期索引和倒计时。对 index 33，`436148` 所在的周期任务会遍历 67 个项，先要求全局任务字节 `+0xF23==1`，再调用 `435bf4` 检查索引位，并检查该索引的运行期待处理状态及倒计时。符合条件时，代码在 `436246` 调用 `435d7e`。所以模型回调使请求进入调度状态，并不等于已经通过了 CAN 控制器门控。

`439984` 对 1A8 映射项 `21 02 14 00 03 00 a8 01` 分别写入几处状态：slot 33 的待处理字节置 1；映射半字 `0x0014` 写到 `2040a5fc + 2*33`；映射字节 `3` 写到另一个 slot 数组；另将 post-send callback 计数槽置 3。这里的 `0x14` 与缓存/事件处理表第 33 项 `+0x0a=0x50` 是不同字段、不同存储地址，不能按相同计时参数处理。在本次已追踪的 `436148` 主循环与 `435d7e` 发送/清理链中，没有闭合 `2040a5fc` 这项半字的读取者和时基；因此只记作映射半字 `0x14`，不称为已证实的 20 单位倒计时。

## 缓存/事件处理表 +0x0a 的内部计时比较与任务开关

缓存/事件处理表第 33 项 `+0x0a=0x50` 的确被消费，但不属于 D8 TX 项，也不是 `435d7e` 或 `434744` 的发送许可。事件处理器 `439610` 的分支在 `439706` 读取 `[descriptor+10]`；非零时把每 index 的时间戳槽地址传给 `4292d0`，并把 `+0x0a` 作为阈值。`4292d0` 从 `2040ffc8` 取当前内部计数，计算当前值、阈值与该槽旧时间戳的差；达到阈值时更新该槽为当前值并返回 1，未达到则返回 0。由此只能说缓存/事件处理路径中的该字段是内部计数域阈值 `0x50`（十进制 80）。

同一计数变量在 `4292f0` 中每次被调用时加 5；该函数还扫描 30 个 timer 槽。静态材料没有闭合 `4292f0` 的实际调度频率/墙钟单位，所以不能把该缓存/事件处理阈值换成毫秒或秒，也不能将它解释为 D8 持续时间。它与 TX callback 清位无已证实关联：`+0x0a` 不在 `43a6b1` 的 3→2→1 计数链中。D8 请求清位仍由 post-send callback 次数控制，任务扫描另受 `+0xf23` 门控；目前无法据此换算确定的墙钟清理时刻。

全局任务 gate 的普通开关入口可直接定位：`4360fc` 将 `204181e8+0xf23` 写为 1，并重置相邻调度位图/状态后转入 `4293f0`；`436124` 对应将相关状态清零并把 `+0xf23` 写 0。`436148` 入口只在该字节恰为 1 时进入 67 项扫描，否则直接返回。已有调用点包括 `4328be` 在上游字段为 `0xffff` 的分支中依次调用 `4360d8`、`4360fc`，以及 `436692/4366b8` 的启停路径；主循环/服务函数 `438618` 在 `43864e` 调用扫描器 `436148`。这些调用可证明固件中有显式启停路径，但不能证明本车当时 gate 的值。gate 为 0 时扫描不发生，故 post-send callback 计数不会因这个扫描器而推进；重新启用后，只有再次走到 callback 才会推进或清掉请求。

## MCU 发送入口与管理器门控

`435d7e` 从 index 映射和 TX 缓冲表取出长度与数据，随后调用 `434744`。`434744` 对 `204172d4` 的判断如下：

1. 管理器状态字 `204172d4+0x0c` 必须等于 2。
2. `204172d4+0x08` 必须非零。
3. `204172d4+0x04` 的 bit 1 决定直接发送路径。若 bit 1 清零，代码再看 bit 3：bit 1 与 bit 3 均为零时返回失败；只有 bit 3 时转入 `4346d0` 的替代处理。

普通初始化代码提供了能通过这些条件的一条路径：`4345c0` 将 `204172d4+4` 写为 `7`、`+8` 写为 `1`；`43856a` 调用它后，再调用 `434624(0,2)` 设置状态 2，并调用 `4360d8` 缓存初始化；TX 扫描另受 `4360fc/436124` 控制。`434624` 的状态 2 分支若旧状态为 1 则不覆盖该状态；状态 3 分支无条件写入 3。可见 `443918`、`443a10` 等停止/错误处理路径会设置状态 3；`443d34` 等重置路径会再请求状态 2。上述是固件中的可达状态迁移，不证明当前车辆运行时走过哪一条。

当 bit 1 为 1 时，`434744` 准备 index 对应的数据并调用 `46d190`。若低层返回非零，`434744` 返回失败；`435d7e` 因此跳过该项的 post-send callback。若低层返回零，`435d7e` 调用索引回调表中的函数（B12 所列 index 33 为 `43a6b1`），再做本地调度状态处理。该回调表示 MCU 软件路径继续处理，并非外部模块 ACK。默认初始化写入的 flags=`7` 包含 bit 1，因此从该初始化状态出发走的是有错误返回传回外层的直接路径；后续 flag 如何改变取决于运行期调用者。

bit 1 清零、bit 3 置位时，`434744` 进入 `4346d0`。此分支可能再调用 `46d190`，但还要求额外状态计数、一个全局半字和另一门控字节非零。重要的是 `434744` 在调用 `4346d0` 后无条件返回 0，不传播内层发送结果。因此 `435d7e` 随后可能执行 post-send callback，即使 `4346d0` 内层没有完成实际提交。仅凭此分支的 callback 不能断言 CAN 发送成功。

## index 33 post-send 倒计数与清位

`435d7e` 只在 `434744` 返回 0 时查 post-send 表；index 33 的 Thumb 回调地址是 `43a6b1`（代码从 `43a6b0` 开始）。回调读取该索引的运行期计数槽（基址由 `43a6e8` literal 提供，索引加到基址后再读偏移 `0xd8`）。其行为是：计数大于 1 时减 1 并返回；计数等于 1 时不再减计数，而是清理 index33 的八字节缓冲；计数为 0 时直接返回。换言之，若计数初值为 3，回调序列是 `3→2→1→清缓冲`，计数槽本身留在 1。清理中 byte0 写 0、byte1 保留 `& 0x02`、byte2 保留 `& 0x06`、byte4 清低两位；因此 D8 请求位 byte1 bit3 会在第三次执行该 callback 时被清除。该“第三次”按软件 callback 次数计，不代表收到了三次外部 ACK。

该时序必须结合前述返回值解释：默认 direct-send 路径只有当 `46d190` 返回 0 时才让 `435d7e` 调用这个 callback；但 bit3 替代路径的 `434744` 会无条件返回 0，故在那里 callback/倒计数也不能作为实际 CAN 提交成功的证据。index33 长度为 8，适用其完整 callback 分支；`435d7e` 对长度超过 8 的通用异常分支会调用发送入口后直接跳过 callback。

## CAN 驱动仍可拒绝提交

即使通过管理器判断，`46d190` 仍会检查控制器索引范围和运行期控制器/发送槽状态。它在控制器对象 `+4` 的 bit 3 置位时直接返回失败；随后调用 `46cb08`，若返回非零也向上报告失败；每索引上下文 `+0x0c` 非零时同样返回失败。`46cb08` 还检查控制器状态、长度/配置，以及待用发送槽是否忙，再决定是否进入 `46f14e`。只有继续到 `46f14e` 才到达 B12 已恢复的标准帧 mailbox 构造路径。由此可见，ROM 静态描述了提交条件和丢弃分支，但不能仅凭描述表静态值证明运行时控制器在线或邮箱可用。

## 未知与重查条件

- 这份 ROM 不提供当前 `204172d4` 状态、控制器 bit 3、index 33 上下文 busy 字节、实际 mailbox 占用和外部 CAN 线上状态；目前只能列出正常初始化与拒绝分支。
- MCU 侧静态证据不能区分 Android/AP 的 `DVRConfig=0` 是否阻止 13/01 UART 更新：本固件该发送/调度路径未见读取同名配置。这个未知仍可由本地 AP 固件或源码区分，前提是能恢复 `DVRConfig` 字段消费者到 UART 封包发送调用点的数据流；如果手头没有该 AP 工件，则仅靠本 MCU ROM 无法回答。线上是否收包、驱动是否就绪和邮箱是否空闲则是运行时状态，不能由静态 ROM 解决。
- 缓存/事件处理表第 33 项 `+0x0a=0x50` 的消费者已追到 `439610→4292d0`，比较基准为内部全局计数 `2040ffc8`；`4292f0` 每次调用加 5。但实际调度频率和墙钟单位未建立，不能换算毫秒，也不能推导 D8 TX 时长。映射项 `+0x02=0x14` 写到 `2040a5fc+2*slot`，其读取者/时基在本次主链中仍未闭合；不能据它推导 D8 清理延时。
- 表身份已复核：`435d7e` 读取 TX 映射、TX 缓冲和 callback 表，不读取 `20409804+0x218`；`435f28`/事件处理使用后者。此报告不再把缓存/事件处理表的 index 33 与 D8 TX index 33 对应。
- 若固件哈希/版本或初始化映射发生变化，应重查对应函数和描述表；同一哈希下，不需要重做 B12 已确认的 D8 位打包和 CAN ID 映射。

以上结论是离线静态代码证据，不是本车当时已使能或成功发出的线上报文证明。

# MCU 2B1 缓存上报与软件状态：离线静态分析

范围：按 B12 及 `MCU_FINDINGS_20261012.md` 所确认的 `DHUBX11G0622CSJ` 固件复核，映射为 `VA=0x420000+file offset`。仅检查现有固件、反汇编和映射；没有读取车辆/运行内存，也没有执行固件。

## 结论

历史原始报告 `55 aa 03 11 13 02 14 00 00 00 02 b1 08 00 00 00 00 00 00 00 00 0b` 能证明的范围很窄：报告项 `index=0x14` 的 byte7 为 0，报告携带的 8 字节缓存值也为 0。构造器会独立读取该软件状态数组和缓存；缓存数据复制没有要求本次先发生 CAN RX。因此，**若报告时缓存已为零，MCU 可在没有新收到外部 CAN 2B1 的情况下把该零值放进报告**。这是代码路径能力，不证明历史报告前从未收帧，也不证明该缓存上电默认就是零。

当前能确认的专用缓存初始化 `0x435cb0` 对 index20 使用 `20 00 00 00 00 00 00 00` 模板，而不是全零。已知复位清零段和两张启动清零表均未覆盖低地址缓存 `0x204003c4`，且 `0x435cb0` 有调用门槛；因此本证据不能确定历史时点缓存为何为零。`0x44a518` 构造 `13/02` 并遍历缓存，但其上游间接调用表/调度尚未找到，不能据此宣称它按周期自主上报。

byte7 只称为**软件状态**。对 index20，报告格式器检查 `status[20]`：非零时置输出 byte7=1，否则为0。状态维护函数中确有写 0 和写 1 的分支，但现有反汇编没有证明这个软件状态等同于 CAN RX 有效、超时或模块在线标志。故历史 byte7=0 只表示格式器读取时 `status[20]==0`，不能解释成未收到 2B1、2B1 超时或模块离线。

离线静态代码已闭合一条**条件式**硬件接收路径：控制器 MMIO/FIFO → 80 字节帧记录 → `0x42a338` 的类别0分发 → 物理 RX 描述表匹配 → index20 callback `0x435fd5` → `0x435fd4` → `0x435f28` 对缓存 `0x204003c4` 的条件更新。它证明固件具备将匹配接收帧送入 2B1 缓存的代码；不证明这条路径在历史报告前实际执行过，也不把 DVR 在线/离线作为结论。

## 表身份与可复核地址

- 物理 RX 描述表基址 `0x20408bbc`，每项 28 字节。index20 在 RAM `0x20408dec`，ROM file offset `0x7b274`，原始项为 `00 00 00 00 00 00 00 08 14 00 b1 02 00 00 00 00 00 00 00 00 d5 5f 43 00 00 00 00`。`0x4348f0` 用此表按类别、ID、DLC 查找并调用 callback；该项对应类别0、ID `0x2b1`、DLC 8、callback `0x435fd5`。这里的 `row[0]`、`row[12]` 属于物理 RX 表，不能直接拿来解释 `0x4366e0`。
- **缓存/状态维护描述表是另一张表：** `*(uint32_t *)(0x20409804+0x218) == 0x20409a20`。index20 位于 RAM `0x20409c50`，ROM file offset `0x7c0d8`，原始项开头 `01 00 00 00 0c 90 48 00 08 00 64 00 01 00 00 00 bd e1 43 00 ...`，所以此表的 `row[0]=1`、`row[12]=1`、`row[4]=0x0048900c`、`row[16]=0x0043e1bd`。`0x435f28` 与 `0x4366e0` 读取此表。`row[0]=1` 在 `0x435f28` 是走逐字节掩码处理分支的条件；不应把它叫作 CAN 有效标志。`row[12]=1` 的业务含义也未由代码注释或接口契约证实。
- 状态指针槽是 `0x20409804+0x1a8 == 0x204099ac`；槽的启动映射值为 `0x2040007a`（file offset `0x7be34`）。因此 `status[20]` 地址为 `0x2040008e`。不要把槽地址 `0x204099ac` 本身写成数组地址。
- 缓存表 `0x2040aa78` 的 index20 项位于 `0x2040ab18`，指向 `0x204003c4`，长度8（ROM file offset `0x7cf00`）。上报数据取自该缓存，不是格式器现场读取 CAN 控制器。
- 新增交叉引用/反汇编摘录见 [`rx-validity-xref-disasm.txt`](rx-validity-xref-disasm.txt)。

## 接收与缓存更新路径

1. **驱动记录由硬件寄存器填充。** 配置初始化路径 `0x42a4e8 → 0x46cf88` 将控制器配置中的回调 `0x42a339` 安装到控制器对象的 `+0x610` 字段。`0x46cc7c` 取硬件基址表项（表 VA `0x4997dc`；channel0 基址 `0x40304000`），准备记录缓冲区并调用 `0x46f544`。该函数从 `hw_base+0x2000`、`hw_base+0x2004` 和后续 FIFO/寄存器位置读出帧信息，写 DLC 至 record `+72`、头/标识字段至 record `+0/+4`、payload 至 record `+8` 起。这里证明固件代码从控制器 MMIO 读取帧记录；无法从静态代码证明控制器当时收到某一特定 2B1 帧。
2. **队列记录进入类别0分发。** `0x42a338` 在 `r1==1` 路径按 80 字节记录步进，从 `0x20410e8c` 一带取接收记录，经 `0x46d3d8` 处理，再取记录 `+4` 的 ID、`+72` 的 DLC、`+8` 的数据指针，以类别 `r0=0` 调用 `0x43480c`。邻近的 `0x42a408` 另一路以类别 `r0=1` 调用同一分发器；2B1 物理描述项类别为0，故类别1这一路不匹配该项。以上只闭合到驱动回调/记录消费者；没有恢复更上层事件为何触发或某次历史调用是否发生。
3. **分发匹配物理 RX 行并调用 index20 callback。** `0x43480c` 将参数规整后调 `0x4348f0`。后者遍历 106 个 28 字节行，比较行 `+6` 类别、`+10` ID 与记录 DLC；对 index20 匹配后从行 `+20` 取 `0x435fd5`，以 `r0=20`、`r1=帧结构指针` 调用。
4. **回调准备缓存写入。** `0x435fd4` 要求对象 `0x204181e8+0xeb7==1`；匹配后将 `0x204181e8+0xe4d[index]` 事件字节置为3，并将帧数据指针交给 `0x435f28(index,data*)`。`0x435fd4` 本身没有直接写 `status[20]`。
5. **`0x435f28` 的目的地与更新条件。** 它从 `0x20409804+0x218` 取 index20 缓存处理行（`row[0]=1`、掩码指针 `row+4=0x48900c`），并从 `0x2040aa78[20]` 取目标 `0x204003c4`。本行走掩码分支，对至多8字节的输入逐字节与掩码相与；再与当前缓存比较，仅在比较结果非零时将变换后的字节写入目标。故这是一个可能覆盖缓存的 RX 路径，但零值本身不能标记来源：接收数据经过掩码后也可能为零，缓存还可能受初始化及其他写入者影响。

## 上报数据和 byte7

- `0x44a518` 构造 `13/02` 项，按迭代 index 直接读取 `*(0x204099ac)[index]`：非零时将输出 byte7 bit0 置1；零时保持清零。index20 的消息 ID、长度取自物理 RX 描述表，payload 从 `0x2040aa78[index]` 指向的缓存拷贝。它未检查“本次是否收到帧”，也未检查“接收事件计数”。
- `0x449dc8` 的另一格式化路径也读取软件状态和缓存；其状态检查使用 `0x20409804+0x218` 描述表，而非 `0x20408bbc` 物理 RX 表。对 index20，`row[12]=1` 未置该检查的屏蔽位，因此非零 `status[20]` 写 byte7=1，零则保持0；随后仍独立复制缓存数据。
- 因而 byte7 是格式器读取时的软件状态快照。代码证实了 byte7 与缓存数据分开取值；没有证据把 byte7 解释为“收到过有效 CAN 帧”、超时位、或模块存活状态。
- `0x44a518` 中可见 index 迭代及结束标记，但本次未找到直接 `BL/B.W` 上游；间接表/回调仍未排除。报告项可由已有缓存构造，不等于已证明周期调度或 AP 请求关系。

## 初始化与历史零值限制

- `0x435cb0` 初始化 93 个缓存项。index20 的模板指针表项指向 ROM `0x48e254`（file offset `0x6e254`），8 字节为 `20 00 00 00 00 00 00 00`；目的地址 `0x204003c4`，长度8。**只有当此初始化路径实际执行后，才能把该模板作为缓存初值。** 已确认入口之一 `0x4360d8` 只有在 gate byte `0x20400079==0` 时才置1、调用 `0x435a80` 并尾调用 `0x435cb0`；gate 已非零时转去 `0x436070`。
- 另一处 `0x436678` 调用链的位测试须按 Thumb 的移位后 N 标志解释：`LSLS #31` 测输入 bit0，`LSLS #27` 测输入 bit4，不是输入 bit31/bit27。缓存初始化分支要求 bit4 路径、`r1!=0` 且对象 `+0xeb7!=1`；相邻 bit0 路径是另一初始化/使能分支。报告不将该初始化概括成无条件 reset 初始化。
- 已有 `data-copy-map.json`、`data-zero-map.json` 和复位段记录未覆盖 `0x204003c4`；它们不能证明上电缓存为零。另一方面，专用初始化模板为 `0x20` 也不能证明历史报告时初始化曾经执行或缓存尚未被覆盖。历史全零可与多种路径相容，无法仅凭报告选出一种。

## 状态维护分支与更正记录

`0x4366e0` 取 `r6=0x20409804`，经 `[r6+0x1a8]` 访问同一软件状态数组；同时以 `[r6+0x218]` 取得缓存/状态维护描述表。index20 的正确表行是 file `0x7c0d8` 的 `01 ... 01 ... bd e1 43 00`，不是物理 RX 表 file `0x7b274` 的 `00 ... 00`。`0x4366e0` 中存在写状态0（如 `0x4367da`）和写状态1（如 `0x436832`）的分支；index20 的 `row[0]=1` 不能排除这些分支。其运行条件还涉及事件/计时字段、回调 `0x4388c1`、维护行 callback `0x43e1bd` 及其它 helper。现有证据不足以把这些分支定义成“CAN 有效”或“超时置位”，也没有证明状态变化只能由一次外部 2B1 RX 引起。

**更正记录：** 早期草稿把物理 RX 行 `0x20408bbc[index20]` 的 `row[0]=0,row[12]=0` 套用到了 `0x4366e0`，并据此声称维护函数不会改 `status[20]`。这是表身份错误，现已撤回。`0x4366e0` 与 `0x435f28` 读取的是独立的 `0x20409804+0x218 → 0x20409a20` 表；其 index20 行来自 file `0x7c0d8`，`row[0]=1,row[12]=1`。报告现不再作“状态不写”的推导。另一个已更正误读：`0x204181e8` 是被 BSS 清零覆盖的对象/计时事件区，不是状态数组指针来源；状态指针来源为 `0x204099ac`。

## 既有日志可区分范围和未解决项

若已有原始 `13/02` 日志保留 index、byte7、8字节数据及顺序，可对 index20 做有限整理：byte7=0/1 可区分报告时软件状态为零/非零；数据全零而 byte7=1 可展示状态与缓存值彼此独立；重复 byte7=0、数据全零仍不能判定“从未收到”或“超时”。若既有日志本身没有 RX 事件/计数/时间戳字段，仅靠这些上报无法恢复收帧史。

仍未闭合：`0x44a518` 的上游间接调用表与调度周期；历史报告时 `0x435cb0` 是否执行；缓存所有其他初始化/写入者；`status[20]` 的产品语义及其与实际外部 RX 的唯一性关系。只有出现新的同版本离线代码/映射或既有日志中保留了能对应 RX 的证据时才重查。本报告不建议通过重复读取全零状态补证，也不从历史上报推出 DVR 实体在线/离线。

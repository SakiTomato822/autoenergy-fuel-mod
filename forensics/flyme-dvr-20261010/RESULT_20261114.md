# 四路记录仪 1.1：EVS 注入兼容性调查（2026-11-14）

## 结论与边界

本轮查到具体软件缺陷，不能把问题归结于没插 U 盘。`com.dashcam.viewer` 1.1（versionCode 2）把代理注入原厂 EVS 服务的默认实例，实际影响原厂 360 使用的相机路径。录制失败和 EVS 进程崩溃是两个需要分别处理的故障。

恢复后，在新一次开机中已确认 EVS 服务稳定、默认实例重新注册、原厂服务打开 `/dev/video12cif`、代理库未加载、无 `dashcamd`。这证明原厂相机链路已恢复运行；未以此替代用户对 360 实际画面的确认。

## 检查记录：未知问题、结果与重查条件

### 1. 注入是否真实生效，是否能影响 360

恢复前读取到 `/vendor/etc/init/android.hardware.automotive.evs@1.0-service.rc` 含 `setenv LD_PRELOAD /vendor/lib64/libevsproxy_preload.so`，PID 367 的 maps 确认该库已加载。`lshal` 的 `IEvsEnumerator/default` 服务端就是 PID 367，原厂 evsrenderengine 为客户端。录制子进程 PID 391、PPID 367 为 zombie。

保存的 `raw/dashcam-viewer-20261114/tombstone_44.txt` 第 755 行起直接记录代理注册 `default`、`wrapped=1`、启动录制进程。说明这里修改的是原厂共享相机服务，不是应用自身的普通权限。

重查条件：APK、代理库、系统 EVS 版本或注入配置变化。相同 maps/常量不重查。

### 2. 崩溃是否由外置存储缺失导致

没有此证据。应用设置界面选择内置存储、未勾选暂停；二进制包含 USB 不可用时回退内置存储的路径。恢复后 `/data` 尚余约 45 GiB；不能据恢复后的剩余空间倒推所有历史写入均成功。

恢复前 `/proc/391/stat` 的 exit_code 为 1024，即正常退出码 4，不是信号崩溃。`dashcamd` 的 `main` 在 0xc198 输出 `startVideoStream failed`，0xc1ac 设返回码 4。打开相机失败为 3，EVS 服务等待超时为 2。故该次退出指向视频流启动失败，外置存储不能解释这个退出分支。保存的 `daemon-disasm.txt` 可复核。

重查条件：新退出码、实际录制日志或新版本改变返回码含义。不为同一故障反复插拔存储或重复启动录像。

### 3. SIGBUS 是否就是看门狗算法错误

不能这样下结论。tombstone 时间为 12:22:06，EVS PID 351，信号 `SIGBUS / BUS_ADRERR`，fault address 与 PC 均为 `0xffaa15a5bda0`。结合映射及 ELF LOAD 段，文件偏移 0x10da0 对应虚拟地址 0x14da0，即 `CameraSession::watchdogLoop()+0x90`。

该位置是 `sleep_for` 返回后的寄存器加法 `add w23,w23,#1`，不访问数据地址；tombstone 的该代码页也不可读。它更符合执行页背后的文件失效/截断等问题，不能仅凭线程名断言看门狗空指针或存储错误。没有捕获当时系统调用，因此文件截断为强候选，尚非唯一确定根因。

安装器却确实存在相符的危险顺序（见下一项），而当时三个安装文件时间均为 12:22。崩溃发生在安装写入时间窗口，但分钟级 mtime 不能证明每条写入的精确先后。

重查条件：作者提供写入时序、旧库哈希/源码或相同崩溃的新证据。不在本车重新覆盖活跃库来复现。

### 4. 已确认的安装与恢复流程缺陷

DEX 的 `SettingsActivity.lambda$runInstaller$18`（code 41888）中：112～120 推送代理库，128～134 推送 daemon，175～181 写 rc，189 才停止 EVS，195 再启动。

`Lc.e`（code 17528）直接执行 `shell:base64 -d > <目标路径>`。重装时对同一路径使用 `>` 会在服务仍映射此库时截断、重写该文件；没有临时文件加原子替换步骤。这是明确的安装缺陷，也与本次 SIGBUS 的特征相符。

恢复分支先改 rc、再删代理和 daemon，最后 stop/start，并仅提示“建议重启”。本轮用户恢复后曾观察到服务反复 `restarting`、默认 HIDL 实例消失；新一次开机后恢复正常。未抓到重启循环的直接 linker 错误，不能将缓存的 LD_PRELOAD 环境认定为已实证根因，但恢复流程的即时成功判定不足。

安装自检还只在 `ps` 输出里搜索 `dashcamd` 字样；僵尸也能被匹配，不能证明正在录制。

重查条件：安装器改为先停服务、原子替换并验证实际注册/进程存活，或取得重启循环的直接错误日志。

### 5. 已确认的相机对象隔离缺陷

`ProxyEnumerator::openCamera` 为不同 ID 创建独立 CameraSession，但 0x169b8 从枚举器同一 `this+8` 取 Backend，并在 0x169f4 传给新 Session。

`DirectBackend::acquireCamera(id)` 的 0x12efc 取缓存 `this+16`；非空时 0x12f04～0x12f2c 直接返回缓存对象，**完全不比较新传入的 cameraId**。只有缓存为空时才在 0x12f5c 调用原厂 `openCamera(id)`。`releaseCamera()` 同样是全局缓存，无 ID 参数和会话级计数。

因此先打开 avm 后请求 apa，会把两个不同 Session 接到同一个底层 Camera 对象，流回调及扩展控制可能互相影响。tombstone 中先有 `DirectBackend: openCamera('avm')`，随后出现 `backend camera opened (apa)`，却没有相应的 DirectBackend openCamera('apa')，与静态分支一致。

同一 tombstone 的 12:21:35、12:21:53 两次底层启动都尝试打开不存在的 `/dev/video6cif`，随后报 `backend startVideoStream failed`。当时节点实际有 `/dev/video12cif` 和 `/dev/video0vicam`。尚未完整重建为何选择 video6 的全部扩展控制序列；不能简单造软链接或改设备名来修复。

重查条件：Backend 按 ID 隔离/明确拒绝不支持的相机，新版本具备可关联的 ID→底层对象→设备→流结果日志。

## 给作者的修复要求

1. 在停止 EVS 后部署文件；使用同目录临时文件、完整性检查及原子 rename，避免截断活跃映射。提供原始 rc 备份和失败回滚。
2. 正确处理 init 配置生效时机，明确说明何时必须整机重启；不能把 stop/start 等同于已重新读取 rc。恢复后验证 HIDL 默认实例和原厂客户端连接。
3. 按真实相机 ID 管理底层对象及引用计数；同一真实相机的多个消费者共享一个流，avm/apa 等不同 ID 应隔离或明确受控仲裁，不能直接返回第一个缓存对象。
4. 录制器在相机未准备好时合理退避重试；回收子进程并监控退出码。自检排除 zombie，验证视频帧/首个有效文件，记录视频流结果和选择的设备。
5. 保留原厂 360 的优先权和失败回退，再开展四路裁切/编码验证。

本轮没有重新注入、写 vendor、重启服务、重启车机或发送车辆控制命令。用户自行执行恢复；调查只读取和离线反汇编。历史原厂 DVR 分支沿用 B1～B30，不把第三方录制器的缺陷推成原厂 DVR 不存在。

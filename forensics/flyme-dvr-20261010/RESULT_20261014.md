## 新增结论

1. **静态代码支持：2B1软件状态有受门控的缺报维护语义。** 接收事件在条件满足时清状态为0；无事件、计数耗尽且模式/延迟条件满足时置1。AP将该位带入普通属性构造，1映为UNAVAILABLE、0映为AVAILABLE。不能把0等同于独立DVR在线。证据raw/mcu-supplement/status-semantics-20261013.md。
2. **静态代码支持：状态事件可触发13/02缓存报告。** 已找到队列type5→48f9fc[index*4]→index20 wrapper44a1c0→449dc8，及发送工作队列对wrapper的数据模式调用。修正此前子报告误读TBB、误归type3分支造成的“找不到表消费者”。这证明报告有事件触发路径，不证明历史每条报告对应新收帧。证据report-trigger-20261014.md。
3. **静态代码支持：维护门控来自PEPS_PowerModeValidity和PEPS_PowerMode。** 2FC解析器字段与MCU模式回调按位对齐；具体模式枚举未猜。AP名称表定位只读属性0x29700149/0x2970014a。
4. **本机实测：2026-10-14 12:41:55，两项PEPS属性均AVAILABLE、bytes=00 00 00 02。** 该数值组合按静态模式函数返回非零，允许进入计数推进的模式条件；另有计数延迟、任务和通信门控，尚不能证明全部开启。
5. **本机实测：12:42:46，一次条件化查询D3=0x297000D3得到AVAILABLE、bytes=00 00 00 00。** 没有新增模块在线证据，不计全零为功能进展，不继续轮询。get函数eaa2c..34会重写返回timestamp为查询时刻，所以该时间戳也不能证明刚收帧。

## 本机访问与采集边界

沿用原生Termux→adb -P5038→127.0.0.1:5555。本轮ADB本地连接状态丢失后重连成功。普通dumpsys查找HIDL接口失败不代表服务缺失；改用已确认的只读HIDL路径成功：

```
lshal debug android.hardware.automotive.vehicle@2.0::IVehicle/default --get 0x29700149 0x2970014a
lshal debug android.hardware.automotive.vehicle@2.0::IVehicle/default --get 0x297000d3
```

现场原始输出保存power-gate-live-20261014.txt（第一次接口查询失败）、power-gate-hidl-live-20261014.txt（成功）、dvr-availability-conditioned-20261014.txt。这些查询不包含未知Binder事务或车辆控制写入。

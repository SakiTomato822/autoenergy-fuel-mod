# DVR 历史对话与证据校正

日期：2026-09-23。回看当前任务中的旧对话及 2026-06 至 2026-09 的原始报告；无实车操作。

1. **原始目标是可用的正常行车记录仪。** 早期对 Android/EVS 的追查只验证了 360 的 `/dev/video12cif` 拼合画面，不等于独立 DVR 录像源。旧 Neusoft DVR 应用可作为协议线索，但其 MT6735/Android 5.1/RPC/Camera(0) 栈不能直接移植到当前 SE1000/Flyme 2.5。
2. **2026-06-30 的“DVR receive-only”是静态分析漏检。** `reports/dvr_vehicle_hal_mcu_mapping_20260630.md` 曾断言十个属性均无发送项。`VHAL_DVR_send_table_correction_20260921.md` 通过重建 BSS 初始化表纠正：其中七项有发送项。`0x297000D8 / INFO_ID_MMI_DVRENTER` 另外映射到 `0x1A8`，之前的 `is_dvr=false` 是提取脚本筛选范围造成。Luna Xhigh 在 `dvr_luna_xhigh_followup_20260923.md` 继续确认 `0x1A8` 被编码为 `01 A8` 并写往 MCU 串行通道；还没有外部 CAN/模块 ACK 证据。
3. **2026-09-19 的 `after_dvr` 不是 DVR 测试。** `analysis/flyme_phone_probe_20260920/实车首次验证结论.md:19` 记录用户车没有 DVR 页面；那一阶段仅是 360 保持打开后的重复快照。因此“点了 DVR 也没反应”的说法没有实测基础。此前普通 APK 读属性遇到 SecurityException 是权限问题，后来 root ADB 读数才有效；不要将两个采集阶段混为一谈。
4. **2026-09-22 root ADB 能读到运行态，但不足以判断硬件。** `car_config` 命令 102 返回 `DVRConfig=0`，枚举含义未知。MCU 侧 `0x2B1` 重复读到全零，当前 VHAL DVR 状态也为零/空。这只能说明当次没有可信非默认 DVR 活动，无法在“配置禁用”“外部模块离线/不存在”“仅缺 UI”之间唯一归因。旧报告顶部已有 2026-09-23 更正，不应沿用正文中过强的硬件缺席判断。

**破局门槛：**先取得外部 DVR 实体/在线的正证据。没有 SD 卡且没有 DVR 页面时，重复抓 360 或再次读取全零 `0x2B1` 不会增加区分力。最小物证是确认 SD 槽实际所属模块的料号、供电及线束；若能借一张已知兼容的卡，再比较正常用车周期前后模块自身状态与新录像文件。并行离线任务是恢复当前 D8 值域/负载与 MCU 对 `0x1A8` 的处理。只有模块在线及命令语义均清楚，才适合评估受控进入测试。
